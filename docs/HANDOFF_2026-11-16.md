## 1. 阻断点：569 个 RGB episode 的物理轨迹不可信（核心发现）

`verify_data` 报 `traj_7 replay boundary C failed`；修正检查逻辑后（见 2.1）在 `traj_0` A 处失败，随后查明真正原因不是检查逻辑。

### 证据链

1. **标签本身是对的**：直接用存储的 `actors/charger` 位姿按官方 `evaluate()` 阈值（dist ≤ 5e-3, angle ≤ 0.2）重算 C，与录制的 `success` 数组**逐帧对比 40/40 一致**（首次出现 C 的帧号、帧数全等）。
2. **原始 WSL 录制是自洽的**：`env_states` 里 charger 最终位姿距目标约 0.5 mm，与 `success=True` 吻合。
3. **原生重放的分叉出现在抓取窗口**：
   - 用 `replay_rgb`（`obs_mode='rgb'`, `render_backend='cpu'`）逐帧 `set_state_dict` 重放 `traj_7`，在 t=81 抓取前后 charger 被“吸收”到夹爪约 **4.2 cm**，最终距离停在 **0.0173 m**，C 永远不成立。
   - 前 80 帧（未抓取）几乎一致；`A`（抓取）标签正确；**只有 C（插入）失败**。
   - 前 40 条中：27 条逐帧 C 完全一致，13 条发散，且发散的 13 条 `success` 全为 False、录制的 `success` 全为 True——即差异**单向**，只出现在原始成功的 episode 上。
4. **交叉验证渲染不是无害的**（`traj_7`）：
   - `reset → 110 步 → 每步前 set_state_dict → step`（等于 `replay_rgb` 的做法）：末态 0.0007 m，**成功**
   - 同一环境下只要不给每步喂 `get_obs()`：末态 0.0172 m，**失败**
   - 结论：**在整段轨迹上逐帧喂观测/渲染，会改变有接触的物理结果**。`replay_rgb` 的“重建接触”对 13/40 的 episode 不成立。
5. **“逐帧恢复状态再 step”这种重建本身就不稳定**：`set_state_dict` 触发 PhysX 状态吸收，逐帧恢复再单步会重算接触并吸收位置，产生最多 4.2 cm 的偏差。它不是精确回放。
6. **没有任何“干净重放”路径能同时拿到物理和像素**：
   - `obs_mode='rgb'` + `render_backend='none'` 在环境**构造**时直接崩（`RuntimeError: failed to get system: no system with name [render] is added to scene`）；已实测并已回退，不要重试。
   - 只跑物理、不渲染，结果**与原始 WSL 录制逐帧完全一致**（`traj_0`–`traj_3` 在 `cpu`/`none` 两种模式下 A/C 边界与 `success` 数组全等）。**抓取接触的物理本身是可以逐帧精确复现的**，问题只出现在“边恢复状态边拿像素”这条组合路径上。

### 影响（必须明确写出，不能含糊）

- 按现状在本次合并的 `data/formal_rgb` 上训练/评估 C（以及依赖插入成功的整链），**会在训练集里混入物理上不成立的“成功”示范**。这不是“loss 高一点”，而是标签与像素不一致。

## 2. 本次修掉的两个真实 bug

原实现只在 `t == end` 处检查阶段标签。但阶段定义是“**首次**为真”，而 C 成功后 A（is_grasping）往往会变 False（插入时松开夹爪），B 也会掉出容差。原逻辑会把合法专家数据判成失败。

现在在 `end-1`（即该阶段首次成立的步）检查。`traj_7`：t=149/150 时 C=False、dist=0.0339，而录制的 success 从 t=149 起为 True，正是这个矛盾暴露了第 1 节的物理问题。

### 2.2 `charger/replay_rgb.py` 曾被我临时改动，已完全回退

为区分“渲染副作用”我加过 `--render` 开关，失败后**已回退到原实现**，并重新验证可运行（1 条 episode 正常产出 240 帧）。现在文件内容与原版等价，只多了一条说明性注释：该函数**只渲染、不 step 物理**，`success`/`terminated`/`env_states` 原样复制。

## 2.5 后续追加实验（第二轮，重要修正）

上文的“渲染/观测改变物理”结论来自不同进程之间的对比，**不成立**。第二轮做了严格受控实验，结论如下，请以本节为准：

### 已确认的事实

1. **同一进程内，渲染与观测对物理没有影响**：`obs_mode` none/rgb、`render_backend` none/cpu、是否调用 `get_obs()`，四种组合在同一进程内得到的距离序列**逐位相同**（diff = 0.0）。同进程重复 3 次也逐位一致（确定性）。
2. **单次物理回放也不能保证复现录制**：不重置、不渲染、只按录制动作从头跑一遍，150 条里只有 **109 条（72.7%）** 的阶段边界与录制完全一致。
3. **失败模式高度一致**：A 边界几乎全部复现（78/78、81/81、101/101…），**只有 C 失败**，且重放的最小距离停在 **1.0–1.2 mm**，而官方阈值是 **5 mm**。也就是说插入几乎成功但没跨过阈值。
4. **原因已定位为环境 auto-reset 语义，不是数据损坏**：`terminated` 不是“整段 episode 跑完”，而是 **ManiSkill 的 success 即 done**。录制里 `terminated` 在首次成功帧就为 True；而录制动作在成功后还多出 1–8 步（均值 4.6）。现在**同样无条件先 step 再检查**，可让 `traj_0` 精确复现到 5e-4 m。
5. **录制数据本身自洽**：录制的 C 边界与录制 `success` 首次为真的索引 **200/200 完全一致**；用录制位姿重算 C 与 `success` 数组也一致。

### 还没确认的

- 剩余 27% 为什么在 1 mm 处停下而没进 5 mm。最可能仍是**二次回放的接触历史不可复现**（首次录制能进 5 mm，第二次不能），但这**尚未被直接证明**。
- 录制 episode 在“成功后动作尾”里是否被环境 auto-reset 过（100 条中 73 条在录制 C 边界处或之前 terminated）。若被 reset 过，尾部那些帧就**不是同一条轨迹的延续**，训练时取动作 chunk 会跨到 reset 后的状态。这是**待验证的高优先级怀疑点**。

### 新工具

`charger/capture_rgb.py`：单次正演采集——reset 一次，按录制动作跑一遍，**同一步内**取像素与标签，重建阶段边界并与录制对比；不匹配会被显式记录（`capture_report`），不会静默丢弃。**它尚未在 569 条上跑过**，只在 12 条上做过冒烟测试。

### 吞吐实测（原生 Windows）

`obs_mode='rgb'` + `render_backend='cpu'`：**约 270 fps**（step+render）。全量 569 条约 35 万步 ≈ **22 分钟**。所以“重跑一遍并逐条校验”成本很低，**下一轮应当直接全跑**。

## 3. 下一步怎么修（按优先级，可直接执行）

用户要的是**真正执行实验**，不是再写计划。修复目标是让 C 的像素和标签自洽。以下按推荐顺序：

### 方案 A（推荐）：让 RGB 在采集时同步产生，而不是事后重建

在采集侧（`charger/collect.py`）一次跑通官方 solver，**同一步里同时拿 `get_obs()` 像素和 `success`**，不再走 `replay_rgb`。这正是 WSL 原始录制的方式，物理自洽。

- WSL 现在不可用，所以要用**原生 Windows** 重新采集：官方 solver 需要 `mplib`，Windows 侧无 wheel。**已验证 SAPIEN 的 CPU 后端在 Windows 上物理正常**，只缺 `mplib`。
- 因此本方案的前提是：在 Windows venv 里拿到可用的 `mplib`（或改用 ManiSkill 自带的 `pd_joint_pos` motion planner 实现替代 `solve`），然后 `python -m charger.collect --obs-mode rgb --render-backend cpu --obs-...`。这一步**必须先解决 mplib**，否则不可行。
- 代价：约 1000 个 seed 重采，按实测渲染速度 4 并发约 **1–1.5 小时**。

### 方案 B：只修 C 的观测，复用现有数据集

- 物理轨迹、`env_states`、`success` 都已验证自洽（第 1 节证据 1、2），**不需要重采状态**。
- 需要的是：在**不破坏接触**的前提下，为每帧产出像素。已知不可行的是“恢复状态 + 渲染”。可行方向是**在物理跑通的同时取像素**：即对每条 episode 用官方动作前缀做一次单线程物理回放，**每步 step 之后取一次像素**，全程不调用 `set_state_dict`（除初始 reset），这正是能逐帧复现 `success` 的那条路径。需要在 SAPIEN 里找到“不设 render_backend 也能在构造后挂上相机/传感器”的用法，或确认 `render_backend='gpu'` 在本机是否仍崩（文档记录过 native access violation，勿盲试）。
- 这条路尚未验证成功，属**待验证假设**，接手的同学应先花 20 分钟做小样本验证再推广，不要直接当结论。

### 明确不要做的

- 不要放宽 C 的成功条件、不要删掉发散的 13/40、不要只在成功的 episode 上训练来“避开”问题。
- 不要把 `verify_data` 的失败当成“检查器太严”而绕过；检查器修好后暴露的是真实数据问题。
- 不要用 `--preload`。

# 7. 2026-11-17 会话：全量实测与结论（本节优先）

## 7.1 撤回第 1 节：渲染不改变物理

`verify_data` 的失败不是渲染造成的。第 1 节已于 2.5 自我修正，本会话用新工具 `charger/validate_rgb.py` 在**全部 569 条**上复核：单次正演（只 reset 一次，之后只 `step`，全程不 `set_state_dict`），**所有成功 episode 在录制首个 success 步的插入距离都 ≤ 5 mm（569/569）**，重放从不产生录制里不存在的成功。物理轨迹是可复现的；第 1 节“渲染/观测改变物理”的结论作废，不要再引用。

## 7.2 A/B 数据可用（实测）

- 去掉 `env` 的 success 提前终止后，按录制动作单次重放：**387/569 与录制 A/B/C 边界完全一致；7 条 B/C/A 边界偏移**（A 2 条、B 0 条、C 5 条，偏移 1–2 步）。其余 175 条**只**在 C 失败，A、B 边界全部正确。
- 结论：**A 阶段与 B 阶段的数据与标签一致**（A 边界错 2/569，B 边界 0/569）。A/B 训练不受 C 的问题影响。

## 7.3 C 数据不可用的根因（已定位，可直接引用）

ManiSkill 的 `success` 即终止：录制里 `terminated` 在**首次成功那一步**就为真，而录制脚本在之后又继续录了 1–8 步（均值 4.7，569/569 条都有“成功后的尾巴”）。

- 这些尾部帧**不是**同一轨迹的合法延续，也**不是** auto-reset 之后的新场景（实测重放距离保持 4.55 cm，离重置状态 3.4 cm 很远）。它们是在一个已经“判成功”的 rollout 里继续 `step` 得到的帧。
- 之所以有 175 条在重放里“成功又消失”：录制时插入实际已成功（`_compute_distance` ≤ 5 mm，仅 C 失败的那批**中位数 1.0 mm**，最大 2.8 mm），但那些 episode 的成功步落在**动作序列末尾**，重放时浮点级差异（1e-8 m 量级）让距离在阈值附近翻转，于是“差一点没跨过 5 mm”。
- 也就是说，**C 的图与标签不是在同一个决策上下文里产生的**：标签来自 rollout 中的那一刻，像素来自之后继续跑的帧。用它训练 C 等于教策略在“已经成功”的画面里继续插入。
- **本会话没有修**。要求：C 的数据必须从“成功即终止”的动作序列重新生成（采集侧在 success 帧停止录入，或重采），不能用现有 `data/formal_rgb` 的 C 段。
- 本会话已把 C 照常训练到 12000 步，但输出**单独放在 `runs/formal_labels_invalid/C`**，`runs/formal/` 下**故意没有 C**，这样链式评估无法悄悄拿到它。要做完整 ABC/BC/B′C 评估，必须先修 C 数据。

- **注意**：`runs/formal/{A,B}` 里本会话开始时残留着一份**只训练了 1 步**的旧产物（`C:\robot_cache` 那次），其 `metrics.jsonl` 首行 step=1 的 loss 与本次 step 1 相同，可据此辨认。旧文件已移到 `runs/logs_legacy/`，正式结果从 step 1 重训到 12000。

### 评估本身还不完全可复现（必须知道）

同一配置重跑，A 段结果只有 **82–83/100** 一致。已排除的因素：模型权重相同；模型对固定输入**逐位确定**（`cudnn.benchmark` True/False 都一样）；物理重放逐位确定；每次 rollout 都 `torch.manual_seed` 过。

已测出的入口差异：
- 同一 seed 的 A rollout，前 8–10 步距离在两次运行里**完全相同**，之后以 1e-8 m 量级开始分叉（`runs/repro/`，`charger/repro.py`），此时手臂离物体还有 12–26 cm、没有任何接触。
- 在进程内连续跑两条 episode 时，差异在第 35–47 步进入。
- 用 `charger/repro.py` 在**两个独立进程**里各重放同一个 seed：21 次与 46 次 replan 的输入/输出**逐位相同**。

结论：单次 rollout 可复现，但**在一个长进程里，env 的某处历史影响后续 episode 的数值**（最可能是 CPU 物理端 / SAPIEN 的缓存与线程调度；尚未定位到具体代码）。所以上述成功率有约 **±3 个百分点**的运行间方差。报告任何成功率时都要注明这一点，正式对比实验（如 BC vs B′C）必须跑多次或多进程并报告方差。**不要**为了“复现”去加 `cudnn.deterministic`，那不是原因。

### A 为什么失败（几何诊断，不是猜测）

失败 episode 的形态：多数**从未接触物体**，但 TCP 已经贴到充电器（最小 TCP–充电器距离 0.0105–0.0383 m，在 1 cm 级）；少数**推了物体**（物体位移 0.12–0.15 m）却没夹住。失败不是随机乱动，而是**对齐精度不够**：夹爪在物体旁、没有完成对中/夹取。
